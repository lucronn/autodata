## Separate source, workflow and run identity

Define exact `BuildContextV3` keys:

```text
protocol_version=3 (int), environment='staging', repository='lucronn/autodata',
repository_id, repository_owner_id, run_id, run_attempt,
workflow_ref='lucronn/autodata/.github/workflows/release-workshop.yml@refs/heads/master',
workflow_sha, source_sha, service_config_sha256,
protected_environment='workshop-staging-publish', activation_sha256,
toolchain_sha256, trust_policy_sha256
```

`LiveContextV3` is exactly BuildContextV3 plus `manifest_sha256`, `candidate_digest` and `candidate_run_id`/`candidate_run_attempt`. Candidate digest is a full sha256 OCI reference. IDs are positive decimal strings (1..20 digits), attempts actual int1..1000, SHAs lowercase40 hex, SHA256 lowercase64 hex. `activation_sha256` refers to independently approved staging activation policy; it is not an argument that unlocks the existing CLI. During adapter implementation no real activation policy is installed or emitted. Pure validation accepts unmistakably synthetic test contexts under injected dependencies; the real code validates actual values only when separately authorized callers install real dependencies.

The final authenticated source-binding evidence is a separate signed statement subject to the release manifest/archive digests, with `source_sha`, config hash, manifest hash, workflow SHA/ref, finalization run ID/attempt, candidate run ID/attempt/digest and the three image subjects. Its digest is carried outside the manifest in ArtifactBindingV3 to avoid self-reference. GitHub REST run `head_sha` authenticates the dispatch's workflow revision, **not** `inputs.source_sha`. Require `head_sha == workflow_sha`; never require or infer `head_sha == source_sha`. Require run `event=workflow_dispatch`, correct repository numeric IDs, expected master head branch/workflow path, successful completion for independent consumption and exact run attempt. In the publishing run itself, expect in_progress; never fake a completed-success response from the same running job. An independent later verifier requires both candidate and finalization runs completed/success before declaring accepted publication.

Use authenticated Actions run metadata, the verified Sigstore certificate's supported source/build/run extensions and the Google WIF exchange's protected-environment identity condition to bind `workflow_sha`, `workflow_ref`, repository/owner IDs, environment, run ID and attempt. These are separate authenticated evidence sources: a Fulcio certificate need not contain every GitHub OIDC claim. Exact reviewed workflow code at workflow_sha must fix the protected environment, and owner policy must attest its protection rules; no selfasserted environment string suffices. Workflow source is checked out by its exact SHA as trusted control code with credential persistence disabled; build source is a separate detached checkout at `source_sha`. Git fetch uses an exact SHA, fixed HTTPS repository, no hooks/submodules/LFS/custom credential helpers. Verify `git rev-parse HEAD` and commit epoch before build. Source tree must be clean; never execute helpers from unreviewed build source. Workflow/master movement during a run does not change pinned identities.

Do not expect the REST run object to contain the dispatch input or protected-environment claim. Reject unavailable identity evidence; do not invent provider fields. A later consumer checks the signed source-binding statement and approved manifest instead. **The run endpoint's current run_attempt does not establish an artifact's originating attempt.** Reruns reuse run ID and may expose older artifacts with identical inner bytes. Exact originating upload attempt is authenticated only by the post-upload signed binding and trusted upload evidence below; run ID/current run_attempt/name/inner hash alone are insufficient. Re-running requires a fresh attempt-specific upload/signature/binding and independent approval, with no old-artifact substitution.

## Artifact transport: real outer ZIP, inner ZIP and hard-fail digests

Retain these distinct hashes and byte lengths in a versioned `ArtifactBindingV3`:

```text
protocol_version=3, repository_id, repository_owner_id, run_id, run_attempt,
workflow_sha, workflow_ref, source_sha, service_config_sha256, manifest_sha256,
artifact_id, artifact_name='workshop-release-'+source_sha+'-run-'+run_id+'-attempt-'+str(run_attempt),
artifact_digest='sha256:'+SHA256(original downloaded outer ZIP), artifact_bytes,
archive_sha256=SHA256(inner release.zip), archive_bytes,
member_sha256={release.json,images.json}, member_bytes={release.json,images.json},
created_at, expires_at, candidate_digest, candidate_run_id, candidate_run_attempt,
rollback_manifest_sha256,
source_statement_uri, source_statement_sha256, source_statement_bundle_sha256,
upload_statement_uri, upload_statement_sha256, upload_statement_bundle_sha256
```

`artifact_bytes` is1..16MiB; inner archive1..8MiB; each inner JSON member1..1MiB, total2MiB. Timestamps are strict UTC; now comes from a supplied trusted clock. Enforce expired=false and expires_at>now throughout verification; enforce maximum publication age24h and remaining artifact lifetime>=1h when handing off an accepted binding. Request retention7days explicitly, and require readback expiry consistent with the configured repository policy; shorter effective retention is rejected if it cannot meet remaining lifetime. No missing digest, null digest, size approximation or hash fallback is accepted. GitHub `size_in_bytes` must be measured against actual archive bytes in the authorized staging compatibility trial before accepting that field as `artifact_bytes`; incompatibility blocks acceptance and requires a reviewed protocol amendment.

Upload `release.zip` as the only file, with upload root its dedicated private directory so the Actions service outer archive contains exactly `release.zip`; compression level0, retention7days, overwrite=false, include-hidden-files=false. Use the reviewed official Actions toolkit from the fixed Node helper. Do not implement undocumented artifact upload/runtime endpoints and do not use `gh release upload` (different service). The helper validates numeric immutable `artifact_id`, returned upload digest and any `digestMismatch` field; true, nonboolean or missing required contract evidence fails. Upload digest, REST artifact digest, independently bound digest and SHA256 of **the original downloaded outer bytes** must agree. Standard download-action warnings are not acceptance evidence. If toolkit version has no hard-fail mismatch behavior, the helper supplies it and independent raw-byte verification remains mandatory.

The official upload helper receives Actions runtime bearer/results endpoint only from the current job's documented runtime environment. It validates those HTTPS service origins against the separately approved toolkit service-origin policy, checks run association and never treats a caller URL/token as upload authority. Runtime bearer scope is upload-service-only; the REST readback uses GITHUB_TOKEN actions:read instead. No credential is forwarded between them. Toolkit debug logging is disabled/captured/redacted and bounded. The helper's fixed operation is not a command-line arbitrary uploader; its default execution remains exit3 until a separately installed staging activation context is present.

After upload, fetch by immutable artifact ID; metadata must bind run ID, expected repository/owner IDs, exact attempt-specific name, digest, size, creation/expiry and nonexpired state. This metadata and the run endpoint do **not** authenticate the originating artifact attempt. No latest/name-selected download, overwrite, automatic rerun substitution or permissive list-first selection. Upload output is a candidate observation, not independent authorization. Readback inside the same run creates `uploaded_unaccepted` only after the post-upload signed statement is produced; independent acceptance requires completed/success and matching approved binding. No self-referential claim that an in-progress workflow already succeeded.

### Post-upload signed binding and originating-attempt evidence

After official toolkit upload succeeds and original outer download/hash/length plus inner archive are verified, sign canonical `PostUploadStatementV3` as an in-toto Statement v1 with predicate type `https://autodata.invalid/attestations/workshop-upload/v3` (fixed protocol identifier, never a fetch URL). Its subject is the exact artifact ID and SHA256 of original outer ZIP bytes. Its exact predicate is `{binding_core, upload_evidence}`. `binding_core` is ArtifactBindingV3 with only the three upload_statement_* locator/hash fields omitted, so it includes repository/owner IDs, artifact ID/name, outer digest/length, uploader run ID+attempt, workflow SHA/ref via context binding, source/config/manifest hashes, inner digest/length/member hashes, candidate identity, rollback manifest hash and the pre-upload source-statement identity. Publish the signed statement and verification bundle to the fixed registry evidence layout by digest, then add their locators/hashes to the returned ArtifactBindingV3. The statement cannot include its own locator/hash and is never put in the unchanged inner release.zip.

`upload_evidence` is exactly `{toolkit_lock_sha256, control_workflow_sha, run_id, run_attempt, upload_request_sha256, returned_artifact_id, returned_digest, runtime_service_origin, artifact_metadata_sha256, upload_started_at, upload_finished_at}`. The request hash commits canonical fixed filename/root-relative `release.zip`, inner hash/length, attempt-specific artifact name, overwrite=false, retention7days, compression0 and authenticated current run/attempt. returned_* are taken directly from the current official SDK upload call, never an input artifact ID or a prior binding. Metadata hash commits the bounded authenticated REST readback projection for that returned ID; outer hash/length are measured from original readback bytes. Timestamps must fall within the authenticated attempt's start/completion interval, allowing the owner-reviewed clock skew<=60s. SDK service origin must equal the approved runtime origin; bearer never appears in this evidence.

The real Node helper creates one internal UploadSession from the current authenticated job runtime and returns the SDK observation over its private bounded IPC channel. Finalization can construct the signed statement only from that newly created session's upload result and the matching raw readback; it accepts no caller-supplied UploadSession/evidence/artifact ID. The code hashes/version-checks the reviewed helper and toolkit lock before opening the session. Official v4 immutable upload with overwrite=false plus attempt-specific name must create a fresh ID; collision or any attempt to reuse an earlier returned ID fails before signing. An authenticated source/hash-equal older artifact remains invalid even if its bytes pass every ZIP check.

Use a fresh Sigstore signing identity whose verified certificate run-invocation URI is **exactly** `https://github.com/lucronn/autodata/actions/runs/RUN/attempts/N`, in addition to the exact reviewed workflow code identity. This authenticates the uploader attempt independently from the run endpoint's current attempt. The selected official signer/certificate extension schema must carry this full URI; if it omits the attempt, that signer/toolchain choice is blocked until an equivalently authenticated attempt-bearing signing identity is independently reviewed. Do not accept a signed predicate's attempt claim alone, a current-run REST attempt, log text or GitHub artifact name as replacement evidence. The verifier checks this certificate identity, statement signature/transparency, exact binding core, SDK/readback evidence, independent approval and completed status of this exact attempt; it rejects a valid attempt1 upload statement when checking attempt2 even if the inner release.zip is identical. Tests exercise this case with valid local signatures, not merely malformed JSON.

For the download, request only `https://api.github.com/repos/lucronn/autodata/actions/artifacts/ID/zip` using a run-scoped token with actions:read. Set GitHub API version2022-11-28 and fixed Accept header. Fetch original ZIP bytes using a redirect-aware bounded stream, **before any toolkit extraction**. Verify complete outer length/hash before decoding. Toolkit download/extraction is not a substitute for those raw bytes. Contract-check `downloadArtifact(...).digestMismatch` when used for a cross-check; true is terminal even if local hash appears correct. Never mark a mismatch as a warning/retry success.

### Outer ZIP parser

Add `decode_actions_outer_zip(data: bytes, expected_inner_sha256: str, expected_inner_bytes: int) -> bytes`. It returns only the verified bytes of the sole `release.zip`; it never writes entries to disk. Use a separate parser from the unchanged two-member inner parser: actual Actions envelope is **one member wrapping** the inner ZIP, not `release.json` and `images.json` at the top level.

Permit ZIP32 stored or raw-deflate, descriptor forms with/without signature, UTF-8 flag if exact ASCII name agrees, Windows or Unix regular-file metadata and consistent nonsemantic timestamp metadata. Require a single local header/central-directory entry/EOCD, filename bytes exactly `release.zip`, method0|8, no encryption, spanning, ZIP64, prefix/trailer/gaps, comments, Unicode-path aliases, duplicate names, symlink/device/directory attrs or unknown flags. Accept only well-formed bounded timestamp extra fields0x5455/0x000a; reject conflicting duplicate or unsupported extras. Reconcile local/central/descriptor CRC and sizes; use bounded inflation with expected length<=8MiB and require stream end/no unused data. CRC, hash and exact length all pass. Then call the existing `verify_release_archive` with separately bound inner/member/manifest inputs.

The accepted envelope subset is a compatibility hypothesis until a captured real toolkit archive passes. Save original staging bytes and toolkit lock/tool hashes as evidence. If the actual service emits a different safe format, reject it and amend/review this contract; do not broaden the parser silently. Never accept a fixture result where caller supplied the inner ZIP separately.

## HTTP origin, token and deadline contract

HTTP uses TLS hostname verification, explicit CA trust, no environment proxies and no ambient `.netrc`. Deny IP literals, userinfo, fragments, control characters, non443 ports, backslash/ambiguous URLs and nonHTTPS. API URLs have no query; the single signed download URL may contain its provider query, held in memory only and redacted everywhere. Cap URL length8192.

Authenticate only exact `api.github.com` API requests with `Authorization: Bearer <GITHUB_TOKEN>`. Never forward that header, Actions runtime bearer, WIF access token, cookies or origin headers to a redirect. Allow at most one API302 to an owner-reviewed exact artifact-storage origin set captured in staging. Forbid a suffix wildcard, arbitrary Azure/GitHub-looking domains, HTTPS downgrade, redirect loops, additional redirects, private/link-local/loopback destinations and metadata-server hosts/IPs. Resolve host before connect, reject disallowed address classes and check connected peer; a DNS resolution timeout counts against the operation deadline. No automatic retry with credentials on redirect failure. Missing exact storage origins is a dependency failure, not permission to discover them live. Signed URLs never enter receipts or logs.

Every operation has one monotonic deadline covering DNS, connect, TLS, redirect, reads, parsing and cleanup; phase timeout cannot reset the overall deadline. Metadata30s/64KiB; artifact upload300s; outer download300s/16MiB; registry manifest/blob60s/4MiB; SBOM300s/4MiB; detached signature/bundle/attestation300s/4MiB each; fixed host check30s/64KiB. Each stdout and stderr stream has an independent hard cap, and combined cap equal to the operation cap. Unknown content length streams still stop on limit+1; supplied Content-Length must match actual length and cap. API 401/403/404/410/429, malformed JSON, unavailable digest, expiry and 5xx fail closed; no unlimited Retry-After, implicit retry or token refresh. Staging activation must approve any bounded retry policy separately.

### Build once, approve digests, finalize without rebuilding

`--provenance=mode=max --sbom=true` may change index bytes on a repeated build. Do not forecast those digests or pretend a template is an approved v1 release manifest. The actual working adapter has two explicit phases within this gate's implementation scope:

1. **build_candidate:** consumes independently approved exact `CandidateBuildInputV3` = `{protocol_version:3, source_sha, platform:'linux/amd64', service_config_sha256, source_epoch, dependency_images, migrations, toolchain, secret_versions, rollback_source_sha, rollback_manifest_sha256, toolchain_policy_sha256, upstream_policy_sha256}`, plus independently supplied `rollback_manifest=None|dict` under the bounded contract below. `dependency_images` is exactly caddy/postgres/nats/minio with the four unchanged v1 image fields; no owned-image digest is required or invented. Validate each projected field against the corresponding existing v1 property schema plus its existing cross-field invariants, config hash, immutable upstream pins, migration inventory/runner hashes and numeric secret-version references. Schema projections are fixed helper code, not caller-selected schema fragments. Never pass this object to v1 validate_manifest as if it were a release manifest. Secrets are references only; no secret value is fetched for building.
2. Build/push each owned image **once** in the approved staging repository, collect actual digest/config-ID/platform and verify registry bytes and per-image evidence. Sign/push a canonical `CandidateRecordV3` OCI object (`application/vnd.autodata.workshop.candidate.v3+json`, <=1MiB) containing `{protocol_version:3, build_input_sha256, context, owned_images, dependency_images, migrations, toolchain, secret_versions, rollback_source_sha, rollback_manifest_sha256, created_at}`; owned_images is exactly api/ingestion/migration with the four v1 image fields plus platform. The signed candidate includes verified subject/evidence hashes and is retrievable only by immutable digest, never a mutable tag. Candidate result is `candidate_built_unaccepted`, deployment_authorized=false. It carries evidence for review and is not a release manifest/approval.
3. A human/independent coordinator verifies the completed successful candidate run, signed candidate digest and owner scope, then approves the **complete v1 manifest** containing those exact three observed image/config/evidence identities and four preapproved dependency identities. This approval is a new exact manifest SHA256 record, not an auto-copy permission, and may reject any observed digest. Source/config/dependencies/migration/toolchain/secret-reference/rollback fields must all equal the independently approved build input. Approval must name candidate digest/run/attempt and have a lifetime<=24h.
4. **finalize_publication:** in a separate protected workflow run, consumes approved v1 manifest/config, immutable candidate digest, independent approval record and separately supplied bounded rollback_manifest when required. Revalidate the completed candidate identity, all signed subjects and registry blobs by digest, exact manifest equality to candidate+approved inputs and approval lifetime. **No Docker build, tag mutation, image copy or per-image evidence regeneration occurs in finalization.** A mismatch fails without changing the approved manifest. Produce deterministic inner release.zip with the validated rollback argument, sign the source-binding statement, upload/read back the actual Actions artifact, sign the post-upload binding and return uploaded_unaccepted. A later independent completed-run verifier checks both signed statements, originating upload attempt and final binding.

The two phases use the same approved staging registry; finalization does not copy staged images into production. Future production publication may build a separately approved production candidate in its own gate, or separately approve digest-preserving cross-repository promotion. Neither is automatically enabled. This resolves the digest chicken-and-egg in the actual staging path while preserving independent v1 manifest approval. Owner IDs and environment inputs block live calls, not writing/testing both real phase implementations with injected local dependencies.

`ApprovalRecordV3` is exactly `{protocol_version:3, repository_id, repository_owner_id, environment:'staging', source_sha, service_config_sha256, manifest_sha256, rollback_manifest_sha256, candidate_digest, candidate_run_id, candidate_run_attempt, build_input_sha256, workflow_sha, trust_policy_sha256, approved_by, issued_at, expires_at}`. `approved_by` is an exact nonempty owner-approved identity string<=200 bytes; issued/expiry are UTC, expiry>issued and lifetime<=24h, issued<=trusted now<expiry. Approval bytes have a detached owner signature verified with the pinned owner public key using the reviewed Cosign verify-blob path. The private approval key never enters GitHub job credentials and is not controlled by the candidate builder or finalizer. Policy lists exact approved public-key SHA256 fingerprints and approver identities; no caller-supplied key is accepted. The owner/coordinator signs this review artifact outside these adapters after candidate evidence review. An unsigned/expired/mismatched approval dictionary cannot unlock finalization. Signed approval authenticates independent digest selection; it does not authorize production deployment. Key provisioning/signing are future owner activation actions, not part of this implementation gate.

### Preserve the independently supplied v1 rollback path

All candidate/finalize/verify entry points accept keyword-only `rollback_manifest: dict | None = None`. It is a separate independently approved input, never inferred from source SHA, fetched by mutable tag, manufactured from the current manifest, or added as a third inner ZIP member. Read its original UTF-8 JSON through strict duplicate/type/depth validation with1MiB maximum, then bind `rollback_manifest_sha256 = rt.sha256(rollback_manifest)` over canonical bytes. The independent owner approval, candidate build input/record, final source statement, post-upload binding and later verifier must all agree on that canonical hash.

For rollback_source_sha=null, require rollback_manifest is None and rollback_manifest_sha256 is exactly null; reject an unbound hidden rollback object. For nonnull previous SHA, require a separately supplied rollback object and approved lowercase64 hash before any credentials/executor/transport callback. Validate rollback object's complete existing v1 schema and `_validate_immutable_images` checks; previous must differ from current source, rollback.source_sha must equal rollback_source_sha, and rollback.platform/config hash/migrations must equal the current candidate projections exactly. These are the existing `runtime-check.py:247-270` conservative image-rollback invariants, without recursively demanding an older manifest from rollback_manifest.rollback_source_sha. During candidate construction use the fixed schema and equivalent exact projected invariants because the current complete owned-image manifest does not exist yet. After independent full-manifest approval, finalization and verification **must call** `rt.validate_manifest(manifest, config, rollback_manifest)` unchanged and pass that same validated rollback object to `produce_release_archive(..., rollback_manifest=rollback_manifest)`.
