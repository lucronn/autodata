# Continuous on-demand article ingestion implementation plan

> **For agentic workers:** Execute scoped tasks with tests and review checkpoints. No implementation until this exact committed synchronized gate passes and the coordinator dispatches a builder.

**Goal:** Add opt-in schema2 continuous on-demand article admission with a durable rolling10jobs/24h cap, one attempt per fresh job and permanent no-replay ledger, while preserving finite schema1 unchanged.

**Architecture:** Add one explicitly selected schema2 mode to the existing root-owned state/exact-job worker. Keep a permanent bounded JSON reservation ledger for no replay; count only the trailing24h reservations for quota. Normal application requests create jobs; this worker does not enumerate catalogs or manufacture identities/jobs.

**Tech stack:** Existing Python/Psycopg, root-owned JSON+flock/fsync state, preview systemd unit, pytest/realPG fixtures.

**Spec:** `docs/operations/2026-11-07-continuous-on-demand-ingestion.md`. Issue https://github.com/lucronn/autodata/issues/186; Project https://github.com/users/lucronn/projects/8. Base b3a5c83bfd5238b72b2eca534c61d9d9637b116e (merged PR359).

## Exact decisions

- Add explicit CLI `--continuous` selecting state schema2, compatible with existing `--initialize`, `--enable`, `--disable` control flags. Default CLI/state behavior remains schema1; no implicit upgrade, auto-rotation, finite-ledger reset/pruning or new initialization over an existing file. Every initializer remains disabled and uses databaseclock activation cutoff/sourceSHA. `--continuous --initialize` requires absent state after separately gated archival; no sourcepin migration.
- Schema2 strict keys: schema2, rollout_id, source_sha, cutoff, providers exactly[bankone,banktwo], max_jobs10, enabled, reservations; NO expires_at. Same UUID/source/timestamp/owner/mode/no-symlink/no-hardlink/duplicate-key validation, state+singleton worker locks, atomic exclusive temp/write/fsync/rename/dirfsync and failclosed IO. SourceSHA must equal exact running source. Schema1 keys/expiry24h/max10/statebytes/behavior stay unchanged.
- Schema2 permanently retains every reservation jobUUID+reserved_at; never prune IDs, even after24h or when dispatch/DBcommit failed. Bound at10000 unique reservations AND2MiB serialized state; failclosed at either ceiling, no truncation/reset. At sustained10/day this supports at most1000 fully utilized days before explicit reviewed capacity work; this is honest bounded capacity, not an infinite storage claim. Legacy schema1 retains current16KiB/max10 bounds. Do not raise schema1 capacity silently.
- Quota counts reservations with `now-24h < reserved_at <= now`; the exact24h-old reservation leaves the rolling window, its UUID stays forever reserved. Use databaseclock only. now<cutoff or now<MAX(reserved_at) across EVERY ledger entry (clock regression/future timestamp) failsclosed; disabled cannot reserve. Reservation persistence precedes cap1 DBupdate/commit and exact-job dispatch as today: uncertainty spends quota, never authorizes redelivery. At most10 reservations in any rolling24h window, including across process restarts/concurrent callers. Validate the complete saved ledger has <=10 reservations in EVERY historical open-left24h window, including unsorted arrays (sort a copy of timestamps for a bounded sliding-window check; never mutate stored order/IDs). Reject malformed over-quota history, not only current quota. No calendar-day reset, periodic expiry extension or quota grants on failures.
- Schema2 polling remains serial2s and SIGTERM-aware. Enabled quota-full waits without reserve/dispatch until capacity returns, rather than exiting and relying on restart; enabled empty queue idles. Disabled exits cleanly; invalid state/capacity/IO failsclosed. Preview unit changes described below are code only; installed finite unit remains untouched until a separate runtime gate. Schema1 state/CLI/admission behavior stays finite unchanged.

## Admission and replay boundaries

Preserve exact existing _PRISTINE clauses for both schemas except schema2 alone omits `a.created_at>cutoff`. Schema2 STILL requires `j.created_at>activation cutoff` and permits a descriptor created earlier only if pristine untouched: active membership/takedown, generation0/current_job exact, NULL current source/canonical pointers, matching providers/profiles, pristine pending queued retry0/lease0/emptycheckpoint/noerrors/noretry/noleases, no OTHER job, source revision/observation/canonical revision/rewrite attempt at all. Therefore a new normal on-demand job may activate an older list-only descriptor; a requeue/recovery/review/spent/history job never qualifies. Descriptorcreated_at/identity/body/history are never altered. Schema1 retains both article/jobcreated_at>cutoff, byte-equivalent predicate semantics.

Use the chosen schema predicate consistently at selection, locked recheck and pre-dispatch validation; never remove a.created_at globally or fall back to job_id=None. Retain provider allowlist, rowlock fencing/order, generation/profile/transformation ownership and sourcejob metadata protections. Ledger includes all historical reserved IDs in exclusion. Keep cap1 checkpoint marker and existing run_article_worker_once exact UUID. Do not widen automatic resume/history recovery or change lifecycle/model/sourcefallback/zero-slot server behavior. A captured-source failure still leaves existing readable source fallback; no replay, automatic second model attempt or claim autonomous firstfailure stop. No new API/catalog consumer/Stripe/paid-auth behavior.
