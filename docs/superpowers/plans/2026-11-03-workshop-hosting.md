# Workshop at cars.tk: proposed initial Google Cloud hosting

Planning only, 2026-11-03. Inspection base: `31ffe7ebcf28f345e0b5055b4dad10ebb7ed101c` in the coordinator checkout. The repository is actively advancing; re-pin the final integrated release before implementation or deployment. No resources, billing configuration, DNS, provider endpoints, credentials or secret values were inspected or changed. The existing public `cars.tk` response (200, Vercel, title `cars.tk`) is coordinator-provided evidence, not a new observation by this planner.

## Recommendation and scope

Use **one Google Compute Engine VM, a separate persistent data disk, Docker Compose, and Caddy terminating HTTPS directly in front of the Go API**. Serve the embedded Workshop and API from the same origin, `https://cars.tk`. Keep the current Vercel site serving until a deliberate, approved cutover. Firebase Hosting is unnecessary for this topology: the Go executable already embeds the Workshop, dashboard and API explorer. The selected R5 contract now uses Firebase Admin Go and Google sign-in. Its actual project/app, provider, authorized domain and workload IAM configuration must be established separately; Firebase project availability alone is not live acceptance.

Proposed starting footprint: Debian 12 on an `e2-standard-4` VM (4 vCPU, 16 GiB), 30 GiB boot disk, separate 200 GiB balanced persistent disk with auto-delete disabled, one reserved external IPv4 address, and private Artifact Registry and Cloud Storage backup storage. These are starting sizing choices, not demonstrated capacity. Put the VM and disk in one selected zone, provisionally `us-central1-a`; the owner must select the actual project, region and data residency before provisioning. Keep the backup location outside the VM's zone. Do not assume a specific project already has billing, APIs, quotas or domain ownership configured.

This is a single-instance launch with a maintenance window and a single-zone availability limit. Disk persistence survives a VM replacement; it does not make the service highly available. Proposed initial recovery objectives are **RPO 24 hours and RTO 4 hours**, subject to an actual restore drill and the commercial owner's acceptance before taking payments. If those objectives or scheduled backup maintenance are unacceptable, choose managed PostgreSQL plus a stronger object-store/worker recovery design before launch. No availability percentage or price is promised here. All cloud, traffic, backup, identity and provider costs remain **not yet quoted**; obtain a project/region-specific estimate before creating billable resources. Budget notifications are alerts, not a spending cap.

Important command distinction: the ingestion Dockerfile's current default `python -m autodata_ingestion.worker` invokes the older `main()` loop. It does **not** call `article_worker_main`, which is defined after that module's `__main__` block. Do not start only the default ingestion worker and assume catalog jobs will run. The Python ingestion image already contains the article worker source, contracts, OCR/PDF dependencies and its required Python libraries; the command override requires no new runtime API. If legacy dataset fast/knowledge consumers are used, run their existing loop as a **second service**, with explicit reviewed flags. Enrichment similarly uses `python -m autodata_enrichment.worker` in its own image. Current Compose health checks for legacy ingestion/enrichment execute `run_once()`. They can do real work and can fail merely because work was completed. Replace these in the production configuration with passive process/heartbeat/queue-age observation; health checks must not schedule ingestion or call a bank/model. `/healthz` is liveness; current API `/readyz` checks TCP dependencies, not schema, auth, payment, S3 authorization, source availability or end-to-end product correctness.

The only inspected GitHub workflow, `.github/workflows/autonomous-verification.yml`, tests and runs an ephemeral Compose smoke. It does not publish release images or deploy GCP. Its `compose.ci.yaml` and fixture credentials are **not** a production deployment file.

## Concrete deployment arrangement

1. Mount the separate disk by filesystem UUID at `/srv/autodata/data`; use subdirectories for PostgreSQL, SeaweedFS and NATS. The systemd service must require that mount and fail if it is missing. It must not quietly initialize empty databases on the boot disk. Keep Caddy ACME state on persistent storage as well. Use root-owned release directories `/srv/autodata/releases/<git-sha>/`, and an atomic `current` link for the selected immutable release. No source bind mounts, `go run`, production builds on the VM, or floating `latest` images.
2. Caddy is the only service publishing host 80/443. Its upstream is `api:8080` on the private Compose network. Redirect HTTP to HTTPS. Keep the canonical host `cars.tk`; add a `www` redirect only if the owner wants and controls that hostname. Preserve API paths, same-origin cookies and security headers. Protected responses remain private/no-store; no edge cache for authenticated catalog, source or media. Bound request sizes/timeouts without breaking the application's legitimate polling/ingestion response bounds.
3. Do not publish PostgreSQL, NATS, monitoring endpoints, S3, SeaweedFS master/volume/admin interfaces, ingestion HTTP, or raw Go 8080 on the host. Use authenticated NATS configuration and authenticated private S3 access; explicitly verify anonymous list/get/write fail. Private networking is not a reason to publish unauthenticated admin ports. Bootstrap `autodata-sources` before declaring readiness; do not rely on an implicit fixture bucket.
4. Set service restart policies, stop grace periods, log rotation and measured CPU/memory limits. One article worker bounds initial model concurrency; admission limits, upstream rate limits and observed queue age determine later scale. Drain/stop writers before migration, backup or maintenance. Do not enable the smoke profile, fake-integrations, ingest-fixture, ingestion-smoke or api-runtime-smoke as production services.
5. Keep standard outbound HTTPS available for the explicitly registered identity issuer, approved connectors/model, Artifact Registry and Google APIs. Bank/model availability and licensed source rights are external dependencies, not delivered by hosting. A production bank configuration is supplied by the owner through Secret Manager after authorization; do not reuse test defaults or probe providers during infrastructure setup.

## Identity and the paid product

R5 selects OIDC authorization-code login with PKCE, server-side PostgreSQL sessions, and fixed callback `https://cars.tk/auth/callback`. Keep same-origin Workshop/API/media so secure HttpOnly cookies work without a frontend token bridge. Register the real callback, issuer, client, role/org claims and test actual sign-in, expiry, logout and role denial in staging. Do not assume Firebase Auth's browser ID-token flow is an interchangeable confidential OIDC authorization-code issuer. If Firebase/Identity Platform is preferred, verify its exact supported integration against R5 first; otherwise choose a compatible issuer through that already planned registration process. Do not change R5's contract in a hosting script.

**Paid launch needs an explicit commercial access decision.** The shared catalog currently has viewer roles, not a catalog purchase/subscription relation. Existing organization-owned dataset entitlements and verified-payment reconciliation are different. Hosting and R5 do not implement a new subscription system, checkout provider, or catalog billing. Before charging, the owner must identify the actual sold product, provisioning/revocation path and existing checkout/payment-event boundary. An administratively provisioned paid pilot is possible only if that is the explicitly selected business process; it must not be represented as working self-service billing. If automated subscription purchase is required and absent, record it as a separate product gap before launch, not an infrastructure task hidden in this plan.

Acceptance for the selected payment path must cover verified payment -> correct organization's access, duplicate delivery idempotence, delayed reconciliation recovery, nonpayment/expired/revoked access denial, refunds/cancellation as promised by the product, and no cross-organization leakage on owned datasets. A `dataset_viewer` role or bank API key is not evidence of purchase. No paid launch from a health check or a local demo token.

## Secrets and IAM

Use a dedicated runtime service account, with no project Editor/Owner, granting access only to the named runtime Secret Manager secrets, pull access to the release registry, required monitoring/logging writes and the explicitly designed backup operation. Restrict operator access through IAP + OS Login; no internet-wide SSH rule. Reserve emergency access with an audited owner-controlled procedure. Restrict CI federation to the selected repository/ref/environment; use a separate deploy principal rather than granting CI arbitrary secret access.

The deployment bootstrap reads only authorized Secret Manager versions into root-owned, restrictive files under `/run/autodata` (tmpfs), then supplies the minimum needed subset to each service. No secret value in Git, image layers, release manifests, command arguments or logs. Compose runtime environment is readable by Docker administrators; treat VM/Docker access accordingly. Avoid a single broad secret file containing all provider/DB/admin secrets in every container. Use a migration role, ordinary application DB roles and appropriate S3 credentials instead of sharing database/S3 root credentials with all processes. Verify the pinned SeaweedFS version's supported credential/permission mechanism; default CI environment variables alone do not establish least privilege. Any needed scoped-key provisioning is a documented bootstrap step, not an assumption.

Keep the NATS and S3 administration configuration private; log only redacted failures. Rotation updates a pinned secret version and restarts the affected service through a bounded rollout; changing a Secret Manager version does not itself update an already running process. Keep media/session key-rotation behavior compatible with the integrated R5 design.

## Backup, restore and data safety

For the proposed small, single-VM launch, choose one simple **application-consistent nightly cold data-disk snapshot**, retained 7 daily and 4 weekly copies, plus a portable PostgreSQL custom-format dump and release/manifest metadata exported to a private Cloud Storage backup bucket with an agreed retention policy. Store no credentials inside the release metadata. Backups are not public and are not on the same data disk alone. Exclude `/run/autodata` and other secret material from portable backup bundles. Encrypt at rest using GCP defaults; choose CMEK only if a real requirement justifies its extra key-recovery dependency.

Exact backup ordering: enter a maintenance response before accepting new state-changing user requests; stop API and all ingestion/reconciliation/outbox/enrichment writers with finite drain deadlines; while PostgreSQL remains up, produce and verify the dump; cleanly stop PostgreSQL, NATS and SeaweedFS; sync and take the single data-disk snapshot while the stateful containers remain stopped. Wait for successful snapshot completion within a bounded deadline, record its exact identifier and release SHA, restart stateful services then applications, and check readiness. A failed stop, dump, snapshot, upload or restart fails the backup receipt and alerts an operator; do not count it as the daily backup. Always attempt service recovery in a finally path and preserve failure evidence. The portable dump can be uploaded after service recovery, but the receipt succeeds only after upload validation. Set a 30-minute overall maintenance deadline and alert much earlier if it exceeds the advertised window; validate an acceptable actual window with representative data before paid launch. Retention deletion must select only owned backups and retain the most recent verified recoverable set.

Implement snapshot privileges as a narrowly scoped backup identity: permission to snapshot the one data disk, create/delete only the owned snapshot set as the platform allows, and write the owned backup-bucket prefix. Document any unavoidable project-level permission explicitly in the implementation review. Runtime application processes do not need those cloud permissions. Isolate the privileged host backup operation from application containers: block container access to the GCE metadata server (including the service-account token endpoint) and keep cloud credentials out of their mounts/environment. This is especially necessary if the VM identity can read secrets or create snapshots; merely giving the backup script a different Unix user does not isolate metadata-issued tokens. Verify those network restrictions without exposing tokens. Do not enable a bucket retention lock without the owner's explicit irreversible-retention decision. Snapshot scheduling alone, or a successful `pg_dump`, is not a restore proof.

Restore acceptance: create an isolated replacement VM/disk from a retained snapshot, fetch the exact release digests/config references, restore ownership/mounts and boot with production provider egress disabled. Verify PostgreSQL migration ledger/schema, recent paid access/session records, representative source/canonical records and all referenced objects, NATS durable state, and the selected payment reconciliation's idempotence without charging again or replaying external side effects. Verify a portable dump can also be loaded into a fresh compatible PG17 instance. Restore a source+canonical+image article end to end under an authorized test identity. Record measured data cutoff and elapsed recovery against RPO/RTO. Recover credentials from authorized Secret Manager access separately; do not assume a disk snapshot contains them. Never restore an old database over newer live paid activity as a routine application rollback.

This plan accepts nightly maintenance and at most the proposed recovery window only after explicit commercial acceptance. If continuous service or materially smaller data-loss exposure is required, replace this backup design with managed PostgreSQL PITR and a coordinated immutable-object/JetStream recovery design before launch; do not claim hourly RPO based solely on untested crash-consistent disk snapshots.

DNS rollback to the preserved Vercel page can restore an informational/maintenance landing page; it cannot provide the new paid application's data/access functionality. A VM failure recovery uses the persistent disk on a replacement or the tested backup restore, not stale Vercel application state.

## Monitoring and launch acceptance

Use Cloud Monitoring/Ops Agent with rotated container logs, an external HTTPS uptime check, and actionable notifications to an identified operator. Protect detailed metrics/admin endpoints. Avoid logging auth callback query strings, cookies, Authorization headers, bank credentials, source payloads or payment-sensitive fields. Record request IDs and sanitized outcomes. Track API error/latency, worker/process restart rate, oldest durable article/legacy queue age, lease/retry failures, NATS JetStream disk/consumer state, outbox/payment reconciliation lag, PostgreSQL availability/connections/disk, object access errors, data-disk utilization, backup age/failure, restore-drill age, TLS expiry and budget alerts. The existing `infra/observability/prometheus-alerts.yaml` is a useful rule source, but neither an installed exporter nor collected measurements are established merely by that file. A TCP-ready API can still have an absent worker or broken auth.

Release acceptance evidence must separately establish:

- **Runtime:** exact release SHA/digests, no fixture services/credentials, explicit durable worker entrypoint, migration success at the released head, expected private-only ports, persistent data survives container and VM restart, safe health probes do no work.
- **Access/product:** actual configured Firebase Google browser login/session/logout and denied cases; Workshop works at the final origin; source/canonical/media are protected; selected paid provisioning/payment path works and is idempotent. No local auth fallback in production. Source loading/processing remains honest when an approved upstream is unavailable.
- **Data/recovery:** authenticated S3 with anonymous denial, representative article/image durability, completed nightly backup and isolated restore proof, measured and accepted RPO/RTO/maintenance duration, tested image rollback without discarding paid activity.
- **Operations:** real alert reaches the operator, disk/queue/backup failure can be detected, secret retrieval/rotation and least-privilege deployment work, incident and rollback instructions are executable, estimated monthly cost is reviewed.
- **Cutover:** explicit domain-owner approval, saved original Vercel/DNS state, working final-domain TLS and callback, verified apex and any approved alias, post-cutover browser acceptance and a rehearsed maintenance/DNS rollback decision.

## Alternatives and later changes

**Cloud SQL for PostgreSQL** removes self-managed database backup/patch/HA work and offers managed backup/PITR options; evaluate it first if tighter recovery or HA is required. It does not replace the VM needed for current durable worker, NATS and S3-compatible state. It adds a separately billed database and connectivity/identity design. Verify PG17 and the required `vector` extension against the selected Cloud SQL offering before migration; review the current driver's host/port/password settings and choose an authenticated proxy/private connection design explicitly. Do not assume Cloud SQL is a zero-change drop-in. A later migration should separately prove data, vector/schema compatibility, cutover and rollback.

**Cloud Run** can host a stateless Go API once durable PostgreSQL, JetStream/object storage and worker execution are externalized. Request-serving instances and ephemeral filesystems are not the durable home for the current all-in-one stack. Always-on/worker deployment options still require an explicit execution/cost/recovery design; this is not a claim that all background work is impossible on Cloud Run. **Vercel/Firebase Hosting alone** likewise do not provide the existing PostgreSQL+JetStream+S3+long-running Python runtime. Splitting only the static Workshop adds identity/routing work without removing these backend requirements. Kubernetes is unnecessary for this initial deployment; no Kubernetes migration or certification is part of this plan.
