# Executable Workshop staging release implementation plan

> **For agentic workers:** Use superpowers:executing-plans task by task after the pinned gate passes. The coordinator may dispatch the two disjoint lanes below; no implementation or runtime apply occurs on this planning turn.

**Goal:** Deliver one executable authenticated Workshop staging release path from reviewed source through accepted publication to existing host preparation and actual readiness.

**Architecture:** Compose the existing authenticated-v3 publication validators with real bounded dependencies and activate the existing protected staging jobs. A fixed operator consumes their verified, independently owner-accepted output and invokes the existing host helpers; it does not replace their disk, approval, secret, migration or readiness contracts.

**Tech Stack:** Python3 standard library, reviewed Node22.23.4, locked @actions/artifact6.3.1, Docker Buildx, Cosign, ORAS, gcloud/IAP, Debian12 and PostgreSQL17.

**Spec:** `docs/operations/workshop-staging-executable.md`, existing `docs/operations/workshop-host-provision-install.md` and `docs/operations/workshop-gcp.md` define the reused host contracts.

## Task 3: fixed staging operator (Lane B)

Executable `python3 -I infra/deploy/gce/staging_deploy.py PHASE SOURCE_SHA` accepts only bootstrap, provision-check, provision, install, images, database, private, start, check. It runs on the trusted operator workstation; remote commands are a finite inventory over IAP/OS Login to the owner-approved instance ID, with strict pinned known_hosts, BatchMode, no agent forwarding and no arbitrary command/destination flags. The fixed owner config/phase approval live under `/etc/autodata/staging-operator`; credentials and approvals are externally delivered. Bootstrap is the sole exception to a pre-known numeric instance ID: its existing separately accepted Compute approval binds project, instance name, resource nonce, cost and region before any credential access. Its returned numeric ID is unaccepted evidence until an independent owner config/acceptance update binds that ID; every later host/IAP phase requires it. Each invocation runs one phase, because images/database approvals and tmpfs secret inputs require separate owner delivery. No phase autogenerates its own approval or silently proceeds to the next destructive step.

- [ ] Test real CLI argv/process/receipt handling red before implementation. Read and validate environment, owner approval expiry, source/config/toolchain/host identity and all required owner runtime fields before any gcloud/token access, using the separately approved bootstrap identity before creation and independently accepted numeric instance ID thereafter. Lock operator state; pin config/approval and input bytes; use fixed bounded process invocation, no shell. Bootstrap invokes existing cloud-bootstrap.sh apply, whose existing staging_bootstrap.py checks retain authority over Compute operations.
- [ ] Before host phases, get actual instance ID through fixed gcloud describe and compare owner acceptance. Provision-check/provision invoke the staged accepted bundle's existing host_provision.py check/apply. Do not reimplement package/disk/mount/guard decisions. The owner delivers the reviewed bundle, exact offline package closure and device approval by the existing runbook; code never invents package/device pins. Bootstrap completion alone is not provision acceptance.
- [ ] For install require successful real publisher verify-publication output and an independent owner acceptance whose existing host_install approval binds the exact verification receipt, release archive/manifest and source. Use only allowlisted fixed destination files consumed by host_install, preserve exact root-owned0600/immutable host-mode contracts and no archive extraction on the host. Staging directory transfer is via bounded SSH stdin to a fixed installed receiver command implemented inside staging_deploy.py, never scp wildcard, arbitrary path or shell interpolation. Receiver is included by the existing automatic Python host-bundle inventory. It rejects unknown members, traversal, links, duplicates, oversized input, changed approvals and existing destination collisions; secret files are not copied from repository output.
- [ ] Invoke existing deploy.sh install SHA, host_prepare_release.py images SHA and database SHA under their separate owner approvals. The operator requires successful phase receipts matching the same host/source/config, but existing helpers remain the authoritative on-host guards. Database and image helper approval replacement is external; fail instead of overwriting approvals. Provision/release/database failure leaves existing journal for explicit recovery, with no blind retry/reformat/down-migrate.

It may relay opaque bounded frames via inherited FD/stdin but never parse/print/store secret values in public state; service-specific approvals remain separate and are not manufactured. Then start invokes existing maintenance-first deploy.sh start SHA; check invokes deploy.sh check SHA. Do not hold host locks around a helper that already acquires them.
