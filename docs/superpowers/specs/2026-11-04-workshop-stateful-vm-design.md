## Decision and alternatives

Build an additive lab helper for a pre-provisioned, disposable, offline Linux VM. It installs a transactional nonsecret stateful profile, accepts generated synthetic credentials privately, boots PostgreSQL/NATS/SeaweedFS, and measures persistence across stop/start and reboot. This gives an executable local deliverable without owner GCP/Firebase/Stripe/bank/model accounts. It does not turn lab credentials, fake publisher observations or a local VM into cloud staging evidence.

Extending deploy.sh/host_install.py would couple the drill to owner-approved cloud configuration and publisher/mount acceptance. Relaxing those contracts would weaken accepted boundaries. Reusing normal developer Compose would leave host/volume/network identity ambiguous and would not rehearse VM reboot. Therefore both alternatives are rejected for this milestone. Existing production/inert-install files and guards remain byte-identical.

## Trust and environment

The trusted local coordinator supplies an already-created disposable KVM VM, a dedicated already-formatted/mounted data disk, tmpfs, reviewed Python/Docker/Compose binaries and cached image IDs. This milestone creates no VM and formats no device. A separate run authorization must bind the VM DMI product UUID, machine-id, boot ID, data UUID, hypervisor configuration digest, offline/no-NIC evidence, source/helper/profile/image/tool hashes and a fresh run UUID. A protected root approval is an operator decision, not cryptographic proof of disposability. The helper independently checks the observable identities and refuses mismatches, non-KVM hosts, physical hosts, unexpected host interfaces/default routes, unknown Docker resources and any production /etc/autodata or /opt/autodata/current object. A fake approval never establishes GCE ownership/IAM.

No VM NIC is attached during the drill; a hypervisor console is the control path. Docker has one internal bridge with fixed IPs and no published ports. Its name is `adlab-<first9hex-runUUID>`: remove canonical UUID hyphens and take the first nine lowercase hex digits, giving exactly15 ASCII bytes within Linux’s15-byte interface-name limit. Full run UUID and inspected resource identity establish ownership; shortened-name collisions fail closed and are never adopted. Offline tests assert exact deterministic derivation, byte length and collision rejection. No production nft/systemd file is installed, edited or reinterpreted. Existing rejected host-runtime guard behavior remains unchanged. Runtime isolation in this lab has separate evidence and cannot certify API-only GCE ADC or a cloud metadata guard.

## Lifecycle and data

The exact helper verbs are install, deliver, start, seed, check, stop and recover. A fixed local approval and SHA/run UUID identify every operation; callers cannot choose paths/commands/projects. Installation commits nonsecret helper/profile bytes atomically after all checks, and is idempotent only on exact tree equality. There is no current-release pointer and no application startup. Deliver consumes one bounded private pipe containing synthetic per-run secrets, writing service-specific tmpfs files with descriptor validation. Start runs only three stateful services, never pull/build. Seed explicitly writes a single deterministic run-bound row/object/message; check verifies without writes, including negative authentication and S3 read-only behavior. Stop preserves all data; recover requires fresh boot authorization and explicit private redelivery of the same synthetic bundle after reboot, then verifies the original fixture bytes/identities without reseeding.

The PostgreSQL fixture uses a dedicated lab database and table, not AutoData migrations. NATS has a dedicated stream/subject; S3 has a dedicated synthetic bucket/object. A Python probe container is ephemeral and has only internal-network access and a read-only tmpfs credential mount; it is not a fourth long-running service. No commerce, ownership, account/session, article or actual licensed source state is created. This drill is persistence and interruption evidence, not a backup/restore or RPO/RTO certification.

Only the exact fixed PostgreSQL wrong-password `docker exec` operation may capture child stderr, as at most8192 bytes in memory. Every other child stderr remains discarded. Charge these bytes against the existing1MiB aggregate output bound. Stream both pipes under the existing selector/deadline/process-group cleanup rules; byte8193, timeout, cancellation, malformed output or failed cleanup fails closed. Never retain a truncated prefix as evidence. Do not store raw diagnostics in executor results, exceptions, logs, stdout, state, receipts, test-failure output or durable evidence. Classify into closed booleans/failure codes, immediately overwrite/clear the mutable capture buffer and release references on success and every failure/cancellation path; this is a memory-lifetime requirement, not a guarantee against privileged inspection or Python allocator copies. No secret interpolation or exception-string logging is allowed.

Pin the PostgreSQL server command to `postgres -c listen_addresses=* -c password_encryption=scram-sha-256 -c lc_messages=C`; security/profile readback checks these exact arguments, and an authenticated startup `SHOW lc_messages` must return exactly `C`. Client `LC_ALL=C` alone cannot control the server-translated authentication text. The approved PostgreSQL17 image supplies its reviewed psql/libpq17 client. Both positive and negative fixed `docker exec` commands use the same validated recorded PostgreSQL container ID, user999:999, literal TCP endpoint127.0.0.1:5432, databaseworkshop_lab and userlab_admin, with no TTY or interactive stdin. Fixed exec environment assignments are `LC_ALL=C`, `PGSSLMODE=disable`, `PGGSSENCMODE=disable`, and `PGPASSFILE=/run/lab/valid.pgpass` for positive or `/run/lab/invalid.pgpass` for negative. They contain no secret values. No inherited libpq service/host/locale/config environment is allowed. Fixed psql argv is `psql -X -w --host=127.0.0.1 --port=5432 --username=lab_admin --dbname=workshop_lab --set=ON_ERROR_STOP=1 --tuples-only --no-align --command=SELECT 1` (the final `--command=SELECT 1` is one argv element); the locale readback substitutes only fixed `--command=SHOW lc_messages`. No caller command or connection flag is accepted. `-w` forbids a prompt, and disabled SSL/GSS negotiation prevents fallback duplication of diagnostics on this isolated loopback connection.

A negative-auth check passes only when an immediately preceding positive `SELECT 1` in the same invocation returns exit0 and exactly `1\n`, with the same validated ID/endpoint/database/user/source/profile/boot binding still valid before and after the negative child. The positive result is never reused across invocations, startup retries, reboot or changed container identity. Negative child must exit2 normally, stdout must be empty, all stderr must be consumed within8192 bytes, and stderr must equal the following two-line ASCII literal (each line ends LF, including the last):

```text
psql: error: connection to server at "127.0.0.1", port 5432 failed: FATAL:  password authentication failed for user "lab_admin"
password retrieved from file "/run/lab/invalid.pgpass"
```

This is an exact match, not substring search or arbitrary whitespace normalization: the fixed semantic diagnostic `FATAL: password authentication failed for user "lab_admin"` is rendered by libpq17 with **two ASCII spaces** after `FATAL:`. The fixed second line is libpq17's `.pgpass` warning for SQLSTATE28P01; it contains the approved path only. No alternate username/path, localized text, extra line, prefix/suffix, transport error, warning, timeout, refusal, different exit code or partial diagnostic is accepted, even if a FATAL substring appears. Runtime wording differing from the reviewed fixed image fails closed and needs a planning correction; it is never generalized automatically. A positive readiness check plus bare nonzero exit cannot pass negative-auth. No raw stderr or semantic diagnostic text enters a receipt; record only the existing typed `negative_auth` result and fixed failure code.

Required intercepted offline tests in `test_stateful_vm.py`: `test_pg_negative_auth_exact_fixed_diagnostic_and_positive_linkage`, `test_pg_negative_auth_refusal_is_failure`, `test_pg_negative_auth_timeout_is_failure_even_with_auth_prefix`, `test_pg_negative_auth_wrong_user_or_extra_text_is_failure`, `test_pg_negative_auth_8192_limit_and_8193_fail_closed`, `test_pg_negative_auth_raw_stderr_and_secrets_never_escape`, `test_pg_negative_auth_buffer_cleared_on_all_paths`, `test_pg_negative_auth_positive_same_endpoint_and_container_required`, `test_pg_locales_and_transport_flags_are_fixed`, and `test_non_pg_negative_children_stderr_discarded`.
