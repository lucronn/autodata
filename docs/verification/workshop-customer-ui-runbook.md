### Rebuild and check

Use Node >=20 (verified with 22.23.1) and npm (verified with 10.9.8):

```sh
npm --prefix apps/api-go/workshop-client ci --ignore-scripts --no-audit --no-fund
node apps/api-go/workshop-client/build.mjs
node apps/api-go/workshop-client/build.mjs --check
node apps/api-go/workshop-client/build.mjs --check
```

The complete lock pins Firebase 12.19.0, `@firebase/app` 0.16.2,
`@firebase/auth` 1.13.6 and esbuild 0.28.2, including registry archive integrity
for transitive packages and optional native esbuild packages. The builder checks
the reviewed Firebase/auth archive integrity values. Install scripts are disabled;
the installed platform-specific esbuild binary is required. Missing native
packages fail the build; no download fallback is used. Node and npm are build
requirements only.

Generation writes `workshop/firebase-web.mjs`, its `.LEGAL.txt` companion and
`firebase-web.provenance.json`. Check mode rebuilds in a newly owned external
temporary directory, compares all three files byte for byte, and removes that
directory on success or failure. It does not regenerate missing checkout files.
The provenance schema is `autodata.firebase-web.provenance`, version 1. It records
included package versions, build options, canonical source/lock/build/manifest
hashes and sizes, actual emitted exports, and SDK/license hashes and sizes.
Timestamps and absolute paths are excluded. Legal output preserves extracted
source notices and shipped license/copyright/notice files for included packages.

### Verification performed

The new Go asset/provenance checks first failed with HTTP 404 for the three absent
assets. After generation, actual unauthenticated HTTP handler requests returned
nonempty JavaScript, text/plain and application/json responses. Tests check the
provenance identity/build contract and compare returned bundle/license SHA256
and byte lengths against the served provenance. Existing Workshop source-review
markers, assets and redirect checks are retained.

```sh
go -C apps/api-go test ./... -run TestWorkshop -count=1
go -C apps/api-go test ./...
node --test apps/api-go/workshop-client.test.mjs
git diff --check
```

All commands passed; the existing browser-module helper suite passed 14 tests.
An independent owned scratch copy passed 16 verification cases: a clean
`npm ci --ignore-scripts`, two fresh checks with identical bytes, seven separately
modified source/manifest/lock/build/artifact files rejected, three missing assets
rejected, actual emitted ESM export/import inspection, missing native esbuild
rejected, and a final successful check. Each negative check preserved the scratch
bytes it received; the authoritative checkout's seven build inputs/outputs were
unchanged throughout. Scratch-only evidence for the coordinator is saved at
`/tmp/autodata-firebase-bundle-verification.json`, generated by
`/tmp/autodata-firebase-bundle-verify.py`.

To repeat the negative cases, copy the four `workshop-client` source/manifest/lock
files and three generated assets to the same relative paths in a fresh temporary
repository, install there with scripts disabled, and run check twice. Independently
append a newline to each of the seven files, then independently remove each
artifact, restoring the original bytes between cases. Every modified/missing
case must exit nonzero and leave its input bytes intact. Temporarily move the
scratch `node_modules/@esbuild/<platform>` package outside `node_modules` to
confirm the missing native binary also fails. Never mutate the authoritative
checkout to run these checks.

Actual ESM inspection used Node's `vm.SourceTextModule`: parse the emitted module,
assert zero dependency specifiers, link with a linker that rejects every import,
and inspect the namespace keys without evaluating the module. The ten names are
`initializeApp`, `initializeAuth`, `inMemoryPersistence`, `setPersistence`,
`GoogleAuthProvider`, `browserPopupRedirectResolver`, `signInWithPopup`,
`reauthenticateWithPopup`, `getIdTokenResult` and `signOut`. Esbuild's metafile also
checks exact emitted exports, zero external imports and absence of source maps.

### Remaining final UI acceptance

This milestone does not wire a module into the current customer application.
Firebase app/auth initialization, in-memory persistence, popup behavior,
provider sign-in, token/cookie exchange, cookie-only reload and actual browser
storage behavior require the later UI implementation and browser lane. The
120 DTO/browser scenarios, 21 integrated API/browser scenarios and live HTTPS
acceptance remain pending under the unified UI plan. The final production image
must prove the complete customer app and its assets. No production readiness or
working sign-in is asserted by this packaging milestone.
