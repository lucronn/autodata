## Goal and existing contracts

Provide an executable staging-first path from the accepted bare GCE VM to an installed host runtime, accepted immutable image cache, and migrated initial database; reuse existing inert release install and maintenance-first activation.

The executable `staging_bootstrap.py` creates the VM, data disk and address; it does not install host packages or initialize its filesystem. `host_install.py` accepts only authenticated owner-accepted inert release/migration material. `private_material.py` delivers accepted private material. `host_activation.py` starts an already provisioned host with cached images and an already correct schema. None is replaced here. `runtime-check.py` supplies manifest/config/image/mount/guard/schema validators and `render_bundle`. `runtime-grants.sql` supplies metrics/relay grants. Existing relay changes are outside scope.

## Fixed interfaces and trust

Three new Python3 standard-library entrypoints: `build_host_bundle.py SOURCE_SHA OUTPUT_DIRECTORY` runs on a trusted checkout; `host_provision.py check|apply SOURCE_SHA` and `host_prepare_release.py images|database SOURCE_SHA` run as root on the host. All reject extra args and malformed 40-hex SHA. Production config is rejected by both host entrypoints in this milestone. No arbitrary command, destination, URL, device or environment override is accepted.

The builder requires HEAD exactly SOURCE_SHA and a clean tracked tree. It writes a new directory with `inventory.json` (schema_version:1, source_sha, sorted files entries path/bytes/sha256/mode) and regular files only; no archive extraction. Hash all shipped files, exclude credentials/config/approvals and stop on existing output. Include the existing GCE *.py runtime helpers except test_* and build tool, release.schema.json, runtime-entrypoint.sh, deploy.sh, metadata-guard.nft, autodata-metadata-guard.service, docker-autodata.conf, Caddyfile, nats.conf.template, seaweedfs-s3.json.template, runtime-grants.sql, new bootstrap-role SQL, and infra/compose/compose.production.yaml. Include exact db/migrations/*.sql and scripts/dev/migrate_sql.sh. Materialize helpers under `/opt/autodata/bin`; preserve the render helper's relative template expectation by shipping the Compose template at `/opt/compose/compose.production.yaml` (Path('/opt/autodata/bin/runtime-check.py').parents[2] / 'compose'). No symlinks. Root owns directories0755 and code/templates0444, shell entrypoints0555. Runtime state/config uses existing0700/0600 contracts. Inventory acceptance is by owner hash, not by trusting its self-described hashes.

Fixed inputs: `/etc/autodata/host.json`, `/etc/autodata/host-provision-approval.json`, `/etc/autodata/host-prepare-approval.json`; staged accepted bundle `/var/lib/autodata-bootstrap/bundle`; package files `/var/lib/autodata-bootstrap/packages`. Root-owned non-writable ancestors, regular single-link0600 approvals/config, no-follow bounded reads, recheck pinned inputs before mutation. Both approvals have exact fields schema_version:1, operation, authorization_id UUIDv4, expires_at UTC (future <=24h), source_sha, service_config_sha256, bundle_inventory_sha256, environment:'staging'; provision also has boot_id, machine_id_sha256, data_device_major_minor, data_device_serial, data_device_bytes, data_filesystem_uuid, packages (sorted name/version/architecture/filename/bytes/sha256). Preparation also has manifest_raw_sha256, publisher_acceptance_sha256 and operation-specific image or database inputs below. Unknown/duplicate fields, type drift, missing observations fail. Owner acceptance and secret delivery remain external; these helpers never fetch cloud metadata credentials or call gcloud/Secret Manager.

## Host preparation

Support Debian12 linux/amd64 only in this first profile; reject other VERSION_ID/architecture. Require owner-observed boot/machine/device facts and exact accepted complete offline .deb closure for Docker Engine/CLI/Compose plugin, containerd, nftables, util-linux, e2fsprogs and Python3. Versions and file SHA256 are owner inputs, never invented defaults or latest tags. Before dpkg: reject running Docker, preexisting containers, mounts or unexpected target files; install temporary root policy-rc.d denying service starts, restore its exact prior state in finally. Use `/usr/bin/dpkg --install` with explicit sorted validated package filenames, no shell; no apt/network/repository modification. Verify `dpkg-query` name/version/architecture against approval and required absolute binaries/plugin version before continuing. Package failure is a stopped incomplete preparation, never a rollback claim.

Bind device through `/dev/disk/by-id/google-autodata-data` after no-follow block-device identity resolution; compare major/minor, serial and bytes with accepted observations, reject root/boot/parent disks, partitions, mounted/swap/holders, and any wipefs/blkid signature. Formatting is permitted only by operation `prepare-new-empty-staging-host`; invoke fixed mkfs.ext4 with the accepted UUID after final identity recheck. No force flag, wipefs mutation, resize, repair or existing-data adoption. Existing matching UUID/mount is permitted only with a prior successful receipt matching the same operation/device and exact on-disk state; otherwise fail without reformatting. Partial failure retains journal and requires owner recovery, never blind retry.

Install `var-lib-autodata.mount` with `What=/dev/disk/by-uuid/UUID`, ext4,nodev,nosuid, no automatic boot-disk fallback; `/run/autodata` is tmpfs mode0700,nodev,nosuid,noexec,size64MiB. Persist only nonsecret state. Only after findmnt exact UUID/type/options verification create data directories: postgres999:9990700; caddy0:00700; nats1000:10000700; minio1000:10000700; operations0:00700. Install existing nft guard, guard service, Docker drop-in; daemon-reload then mount, guard start/actual table validation, Docker start in that order. Do not enable/start applications or auto-resume service after reboot. Reboot restores mount/guard dependencies; missing tmpfs secrets prevents application activation. Package/host action commands max120s each, overall900s, output1MiB per command, bounded process-group termination/reap; journal stage receipts are fsynced0600 under `/var/lib/autodata-bootstrap/receipts` and redact stdout/stderr.

## Accepted release and images

Provisioning does not authorize publisher ingress: owner stages exactly the existing publisher-accepted record, inert release approval and migration inputs consumed by `deploy.sh install SHA`. Preparation calls that existing installer and accepts only its successful receipt. Hold the shared `/run/autodata/state/operation.lock` and persistent activation lock in the existing order; do not recursively call a helper while holding a lock it also acquires.

Image approval operation `cache-accepted-staging-images` additionally binds sorted role/reference/image_id records exactly equal to manifest.images and a root-owned tmpfs Docker config directory `/run/autodata/registry` whose only file is config.json0600. An external deploy identity delivers short-lived registry authentication there; no token appears in argv/env/log/receipt. Use fixed Docker host socket and `--config /run/autodata/registry`, pull only each accepted repository@sha256 reference with `--platform linux/amd64`. Each pull max300s, overall2400s, output1MiB; inspect immediately and run existing validate_cached_images. Never retag, prune, remove images or accept a local tag substitute. Always remove only pinned operation-owned config material on success/failure, and fail closed if cleanup cannot be established. No cache success receipt on partial pull. Cached immutable pulls may be reverified/reused on an explicitly approved retry.

## First database installation

Operation `initialize-fresh-staging-database` approval additionally binds release manifest, bootstrap-role SQL, runtime-grants SQL, pgdata_initial_empty:true and exact prior image-cache receipt SHA256. Require no selected current release, no application containers, an empty verified data volume, normal postgres secret and separate migration/admin/scoped-role password files delivered to tmpfs. Existing PGDATA is rejected unless a matching same-authorization journal proves this operation created it; resume requires explicit new approval binding that journal and exact observed ledger prefix. Never silently migrate an existing deployment.

Render Compose/Caddy through runtime.render_bundle from installed files and manifest/config; stage exact files in the inert release using same verified immutable materialization rules as activation. Keep Caddy absent/maintenance; start only postgres with --no-deps --pull never. PostgreSQL initial admin is autodata_admin/database autodata. Using this temporary administrator, precreate only the repository-required pgcrypto and vector extensions at the versions shipped by the accepted PostgreSQL17 image; migration001 then observes them with IF NOT EXISTS. Do not grant SUPERUSER to the migrator. Provision fixed LOGIN roles autodata_migrator, autodata_api, autodata_http, autodata_article, autodata_reconciler, autodata_metrics and autodata_outbox, no SUPERUSER/CREATEDB/CREATEROLE/REPLICATION/BYPASSRLS/memberships. Autodata_migrator owns application schema/tables through migration execution; runtime roles own none. Passwords supplied as file/stdio to fixed psql protocol, never interpolated SQL/shell/argv or command output. Revoke PUBLIC database/schema privileges, grant migrator CONNECT and CREATE on database autodata and ownership of public schema. After migrations grant the four application roles CONNECT, schema USAGE, SELECT/INSERT/UPDATE/DELETE on application tables, USAGE/SELECT on application sequences; grant no DDL, TRUNCATE, REFERENCES, TRIGGER or MAINTAIN and explicitly REVOKE INSERT/UPDATE/DELETE on public.schema_migrations from those four application roles after the blanket DML grant. Revoke all PUBLIC schema/database privileges; use existing narrow runtime-grants for metrics/outbox after migration. New SQL contains static privilege/role statements; use psql-safe generated literal encoding for password assignment, without printing values.

Run Compose migration profile one-shot using only manifest migration image, existing runtime-entrypoint and exact runner command; its migration password belongs to autodata_migrator, not admin. Enforce no-deps,pull never, finite timeout600s and output1MiB, no application startup. The accepted manifest must bind that migration image and exact local tree/runner. On success apply existing runtime-grants as admin, observe actual PG17 catalog/ledger through existing collector, compare exact manifest schema. Remove operation-owned transient admin/migration/role-input files and one-shot container; retain PostgreSQL and maintenance on failure for diagnosis, never down-migrate/delete volume. Database success means schema initialized only; call no provider, payment or model endpoint, and do not mark readiness/production_ready. Existing deploy start/check remains a separate operation after all secrets/storage and runtime prerequisites are established.

## Acceptance and owner inputs

Implementation validation uses fake commands/temp filesystem plus disposable local Docker PG17 only. No GCE/registry/provider credentials are necessary to build/test the code. Required negative cases: bad owner/bundle/hash/mode/symlink; wrong environment/OS/device/UUID/signature; package auto-start attempt; concurrent operation; missing/replaced mount/guard; image digest/platform/config mismatch or timeout and config cleanup; database foreign ledger/preexisting state/incorrect role authority; failed/partial migration and explicit-prefix retry; reboot missing tmpfs. Real PG17 cases prove migrations001-040, least metrics/relay grants, malformed ledger refusal and failure retaining maintenance. A disposable Debian12 VM probe is required before live staging to establish package postinst/systemd/mount behavior; fake tests alone do not prove it.

Owner supplies the accepted Debian image/complete package closure, actual device observation/format authority, publisher acceptance/image pins, external registry auth, exact host/Firebase/provider/Stripe TEST secret delivery, and staging operation authorization. Separate recovery work supplies verified backup/restore/RPO/RTO before any production promotion. Production, DNS, live payments, secret retrieval, relay changes and backup implementation are outside this gate.
