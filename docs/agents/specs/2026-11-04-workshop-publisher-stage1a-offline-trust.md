# Stage1A offline publisher trust contract

Status: synchronized docs-only contract after independent corrected-draft review and verified Issue186/Project8 readback; committed full-SHA preflight, independent exact-checkpoint review and root dispatch remain required. This is not implementation or activation authorization. Baseline is accepted Stage0 receipt `dde53d745f8422ce29d6e8b3d459f4a0b91ebd04`. This spec narrows Stage1 in the research draft to passive offline trust primitives. The canonical gate remains `docs/agents/pre-implementation-gate.md`.

## Boundary and implementation shape

Create only `publisher_policy.mjs`, `publisher_identity.mjs` and their two `test_*.mjs` files under `infra/deploy/gce/`. Use Linux x64 Node22.23.4 with reviewed executable SHA256 `94efd062ed066c1a0b332e18249859c905e920eeada5df55d24c99b919629a90`, built-in `node:crypto`, `node:fs/promises`, `node:fs`, `node:path` and `node:util` only. No package/dependency changes, subprocesses, network APIs, SDK imports, environment credential reads, policy/key provisioning, transport or factory composition. Test files may use `node:test`, `node:assert/strict`, `node:os` and built-in filesystem/crypto modules. Existing modules and workflows remain byte-identical to Stage0.

There are two deliberately distinct results. Pure byte verifiers return frozen **passive validation records** under explicitly supplied test/trusted inputs; the exact original trust bytes are retained as canonical-base64 strings for full revalidation on each OIDC call; they carry no installed-policy or runtime authority. `loadInstalledOwnerPolicy()` alone creates a module-private WeakMap handle after the fixed installed path checks and signature verification. No exported constructor, fixture bypass, caller-selected root/path, injectable filesystem or boolean receipt can mint that handle. `installedPolicyClaims(handle)` returns a deep-frozen copy and rejects any unknown handle. `verifyInstalledGithubOidc()` consumes this handle; it still returns only verified OIDC claims, never an Actions-runtime capability or authorization to publish. The new modules have no executable CLI behavior or top-level operation.

All boundary errors expose only `missing_dependency`, `invalid_trust_input`, `invalid_oidc_input`, `operation_timed_out`, `operation_cancelled`, or `cleanup_failed`. Never echo token bytes, claim values, exception causes or paths. Unavailable installation and every runtime-bearer request return `missing_dependency`. No result is publication, installed-toolchain, provider-acceptance or activation evidence.

## Strict bytes and bounded parsing

Use one exported `parseStrictJsonBytes(raw, limits)` parser in `publisher_policy.mjs`; the identity module imports it. Require `Buffer`, strict UTF-8, a single JSON value without BOM/trailing bytes except JSON whitespace, no duplicate decoded object keys, prototype-neutral objects, depth at most16, at most256 total object keys, individual strings at most8192 UTF-8 bytes and arrays at most16 elements. All numbers must be safe integers; reject exponent/fraction number syntax, negative zero, unpaired UTF-16 surrogates and unrecognized schema members. Field-specific schemas further constrain types/ranges. Envelope limit65536 bytes; signed payload32768; bootstrap16384; normalized JWKS65536; compact JWT16384. No compression or recursive envelope resolution.

Canonical base64 means RFC4648 standard alphabet, required padding and exact re-encode equality. Canonical base64url means URL-safe alphabet without padding and exact re-encode equality. Reject whitespace, mixed alphabets, alternate spellings and oversized decoded data before cryptographic conversion.

## Bootstrap source and filesystem contract

Proposed fixed production source is `/etc/autodata/publisher/bootstrap-v1.json`; sibling names are exactly `policy-v1.envelope.json` and `github-oidc-jwks-v1.json`. Paths are constants in the new module and cannot come from cwd, environment, IPC, argv, a policy URL or a request. No such files are installed by Stage1A.

Bootstrap is strict JSON with exactly `protocol_version:1`, `purpose:"autodata.publisher.bootstrap.v1"`, `key_id`, `owner_public_key`, `policy_sha256`, and `minimum_epoch`. `owner_public_key` is canonical standard-base64 raw Ed25519 public key32 bytes; `key_id` is lowercase SHA256 of those32 bytes; `policy_sha256` is lowercase SHA256 of the exact envelope bytes; `minimum_epoch` is a safe integer1..2147483647. This root document is trusted because the owner independently provisions the immutable root path, not because its self-described fingerprint matches. There is no committed production key, default root or environment override.

Open `/` then each fixed directory component through an already owned descriptor (`/proc/self/fd/<owned-fd>/<fixed-component>`) with `O_RDONLY|O_DIRECTORY|O_NOFOLLOW|O_NONBLOCK|O_CLOEXEC` where supported by Node22/Linux. Open final files through the final owned directory descriptor with `O_RDONLY|O_NOFOLLOW|O_NONBLOCK|O_CLOEXEC`. Never resolve an untrusted path through `realpath` as a substitute. Validate each descriptor with `fstat`: root UID0, directories have no group/other write bits and no setuid/setgid/sticky bits; files are regular, `nlink===1`, mode0444 or0400, no special mode bits, exact positive bounded size, and UID0. Filesystem mode is not immutability evidence.

Read bounded `/proc/self/mountinfo` (at most1MiB) and each owned descriptor's `/proc/self/fdinfo/<fd>` (at most4096 bytes); match each descriptor's numeric `mnt_id` to a unique parsed mount record. Require the final `/etc/autodata/publisher` directory and all three trust files to be on read-only mounts; intermediate `/`, `/etc` and `/etc/autodata` directories may reside on writable mounts but must satisfy the root-owned directory checks. Reject a writable nested mount under the fixed trust directory. Trust installation on a writable mount is rejected even with mode0444. Recheck mount records and descriptor identity/type/mode/owner/link-count/size after reading; re-open the constant chain to establish that the selected original path still resolves to the same device/inode chain. Descriptor identities and mount IDs are observations from the kernel, never caller receipts.

Read sequentially in at most32768-byte chunks; require EOF at the declared size and reject growth, shrinkage or replacement. An exported `OwnedTrustReadScope` resource-owner class provides `trackOpen(promise)`, `track(promise)`, `check()` and `finish()` for independent cleanup tests; its constructor accepts `{signal,budgetMs,cleanupReserveMs}`, requiring integer bounds1..5000 and1..1000. It owns pending filesystem promises and handles only and cannot create installed-policy handles. Track at most16 simultaneous operations. The loader calls `check()` to reserve capacity before starting an operation, then immediately registers its promise with no intervening await; reject capacity exhaustion before calling the filesystem. The production loader constructs the scope with constants5000/1000 and exposes no injected scope, filesystem, opener, clock or budget. Register each open/read promise and its settlement handlers before awaiting it; retain every acquired descriptor until safe close is known.

Let `t0` be the original monotonic start. Verification cutoff is `t0+5000ms`; the final cleanup cutoff is `t0+6000ms`, never a reset per-file or per-error budget. Cancellation may move the verification cutoff earlier and allows at most1000ms cleanup, capped at the original final cutoff. Success requires all tracked operations settled, all owned handles successfully closed, no abort/expiry and full validation before the verification cutoff. Normal input failure attempts cleanup within its remaining reserve; unresolved work or failed closure overrides the original error with `cleanup_failed`.

Node filesystem promises are not assumed cancellable. `finish()` must stop awaiting at the final cleanup cutoff and reject `cleanup_failed` if any promise/close remains unsettled; it must not claim a complete drain or a hard real-time guarantee. This is a bounded promise-settlement contract when the event loop is runnable; JavaScript and kernel scheduling cannot promise return at an exact wall-clock instant. A never-settling open/read/close must never cause `finish()` to wait forever or yield an installed handle. Clear deadline timers at return, but retain settlement/rejection handlers and strong references in a module-private quarantine registry. Late completions can only update cleanup bookkeeping, discard read bytes and close an acquired handle once it has no outstanding read; they cannot parse/verify data, start another filesystem operation except owned closure, emit a success, invoke a caller or create any policy handle. Consume late rejection to avoid an unhandled rejection. A close which fails remains recorded as unresolved cleanup; do not retry without a new process.

For the installed loader, permit one active scope per module instance and at most one quarantined installed scope. While either is present, a new load immediately rejects `cleanup_failed` without opening files. A quarantine is removed only after all tracked work settles and every owned handle is successfully closed; a permanently pending promise or failed close leaves the loader blocked for the process lifetime. Removal never changes the original failed result or resurrects its authority. The registry can retain an unclosed descriptor indefinitely when the kernel operation never settles; that explicit failed-cleanup condition is not readiness, safe release or proved resource termination. No subprocess or isolation claim is made in this milestone. Test scopes exercise the same resource-owner state transitions with harmless fake handles; they cannot supply an installed-loader scope or create a handle.

Required scope tests use short budgets with scheduler tolerance: a never-settling open, read and close each yield bounded `cleanup_failed`; a later-resolving open is closed exactly once after the earlier failure; a late rejection is consumed; late read bytes are discarded; a failed close remains failed; neither timeout/cancellation path produces an installed handle; and a quarantined installed scope blocks subsequent acquisition. A test of parser-supplied mount metadata demonstrates parser behavior only, not a real immutable installation.

## Envelope and owner policy

Envelope exact fields: `protocol_version:1`, `key_id`, `payload`, `signature`. `key_id` must equal bootstrap `key_id`. `payload` decodes to1..32768 bytes; `signature` decodes to exactly64 bytes. Hash the exact envelope and compare with bootstrap `policy_sha256`. Verify Ed25519 using `crypto.verify(null, message, publicKey, signature)` with raw public key wrapped in standard Ed25519 SPKI. `message` is ASCII `AutoData-Publisher-Owner-Policy-v1` followed by one NUL byte followed by the **exact decoded payload bytes**. No JSON reserialization participates in signature verification. Parse/validate payload only after signature success. The bounded envelope parser must necessarily run before signature verification; none of its fields selects code, tools, endpoints or trust roots.

Payload exact fields: `protocol_version`, `purpose`, `epoch`, `issued_at`, `expires_at`, `repository`, `repository_id`, `repository_owner_id`, `environment`, `protected_environment`, `workflow_ref`, `workflow_sha`, `ref`, `event_name`, `upload_enabled`, `runtime_bearer_authentication`, `oidc`. Values: protocol1; purpose `autodata.publisher.stage1a.offline`; epoch between bootstrap minimum and2147483647; integer UTC Unix seconds with `issued_at <= now < expires_at` and `0 < expires_at-issued_at <= 86400`; repository `lucronn/autodata`; numeric IDs canonical positive decimal strings of at most20 digits; environment `staging`; protected environment `workshop-staging-publish`; workflow ref `lucronn/autodata/.github/workflows/release-workshop.yml@refs/heads/master`; workflow SHA40 lowercase hex; ref `refs/heads/master`; event `workflow_dispatch`; `upload_enabled` exactlyfalse; `runtime_bearer_authentication` exactly`unsupported`. Reject production or any positive upload/runtime-auth flag.

`oidc` exact fields: `issuer`, `audience`, `subject`, `jwks_sha256`, `jwks_issued_at`, `jwks_expires_at`. Issuer is exactly `https://token.actions.githubusercontent.com`; audience is exactly `urn:autodata:publisher:stage1a:offline`; subject is an owner-selected exact nonempty ASCII string of at most512 bytes, with no control bytes. Recommended default-form subject is `repo:lucronn/autodata:environment:workshop-staging-publish`; custom/immutable subject formats require an exact signed value, never substring matching. JWKS digest is lowercase64 hex of the exact normalized snapshot bytes. Its integer times require `jwks_issued_at <= issued_at <= now < expires_at <= jwks_expires_at`, and `0 < jwks_expires_at-jwks_issued_at <= 86400`. Policy or snapshot expiry fails closed; no online key refresh.

Compute `activation_sha256` for passive inspection as SHA256 of exact envelope bytes. It is never included in its own payload. Do not create existing adapter policy projections, tool pins or uploader descriptors in this milestone. Root replacement, accepted envelope digest/epoch updates and JWKS snapshots are owner-provisioned later. An offline process cannot discover later revocation or rollback of the whole immutable installation; acceptance of a policy multiple times within its validity is not a one-time authorization claim.

## Exact passive trust-byte argument and revalidation

`verifyOwnerPolicyBytes(bootstrapBytes, envelopeBytes, jwksBytes, nowSeconds)` is synchronous and accepts three Buffers plus a nonnegative safe-integer Unix-seconds clock. Check the Buffer type and its respective byte bound before making an independent copy for parsing. After all bootstrap, Ed25519, policy, JWKS-digest/schema and time checks succeed, return exactly `{policy, jwks, activation_sha256, trust_bytes}` as a recursively frozen JSON record. `trust_bytes` has exactly three fields: `bootstrap_base64`, `envelope_base64`, `jwks_base64`. Each is the canonical standard-base64 encoding of its original Buffer; its decoded bound is respectively16384,65536,65536 bytes. No Buffer or mutable typed array is stored in the result. Parsed `policy` and `jwks` use their exact schemas above; `activation_sha256` is the exact-envelope hash. This record reports signature validity under the explicitly supplied bootstrap; it does not authenticate where that bootstrap came from.

The second argument of `verifyGithubOidcBytes(tokenBytes, validatedPolicy, expectedContext, nowSeconds)` is **exactly the `trust_bytes` subobject**, named `PolicyTrustBytes`, not the full return record and not parsed policy/JWKS. Require an ordinary own-data-property JSON object with exactly the three canonical-base64 string fields above and no accessors, prototype tricks, extra fields, `verified` flags or opaque handles. Decode bounded copies and call `verifyOwnerPolicyBytes(decodedBootstrap, decodedEnvelope, decodedJwks, nowSeconds)` anew on every invocation. Use only that fresh return's parsed policy/JWKS. Reverify the owner key fingerprint, exact envelope digest, domain-separated Ed25519 signature, minimum epoch, all policy fields, JWKS digest/schema and current policy/snapshot lifetimes; never trust cached parsed values or a caller's claimed earlier verification. A copied or modified `PolicyTrustBytes` object is acceptable only if this complete verification succeeds under its explicitly supplied bootstrap; changing the trust bytes cannot yield installed authority.

`installedPolicyClaims(handle)` returns exactly the deep-frozen `{policy,jwks,activation_sha256}` copy and never exposes `trust_bytes` or the module-private marker. The loader stores independent canonical trust-byte strings in its private WeakMap after fixed-path kernel checks, full verification and successful timely cleanup. `verifyInstalledGithubOidc` looks up that private entry, rejects any forged/copied/passive value, and passes its stored `PolicyTrustBytes` through the same full revalidation with its internal current clock. It never accepts a caller-supplied bootstrap or parsed-policy substitute. Installed trust is a provenance property of this fixed loader, not a property of passive byte-validation data. No result supplies an Actions runtime identity or upload capability.

Required OIDC tests call `verifyGithubOidcBytes(jwt, policyResult.trust_bytes, context, now)`. Reject the full `policyResult`, a bare `{policy,jwks}`, an opaque/copy handle, altered bootstrap/envelope/JWKS bytes, an old-valid record checked after policy/snapshot expiry, unknown/accessor fields and `verified:true`. Demonstrate that passing fresh valid trust bytes yields only passive claims, while only the fixed loader can construct the installed-policy handle. An attacker-supplied self-consistent bootstrap can validate only its own passive fixture chain; this is never evidence of installed owner trust.

## Normalized OIDC JWKS and JWT contract

Normalized snapshot exact shape is `{"keys":[...]}` with1..16 keys sorted strictly by `kid`; each key has exactly `kty`, `kid`, `use`, `alg`, `n`, `e`. Require `kty:"RSA"`, `use:"sig"`, `alg:"RS256"`, ASCII `kid` matching `[A-Za-z0-9_-]{1,128}`, `e:"AQAB"`, canonical unpadded base64url modulus256..512 bytes, no leading zero and an odd modulus with the top bit set. Reject duplicate IDs and private key fields. Snapshot normalization/provisioning is outside Stage1A; the owner authenticates its exact digest in the signed policy. No x509 certificate or JWK-supplied URL is a trust source. Build the public key with `crypto.createPublicKey({key:jwk,format:"jwk"})` and require RSA modulus2048..4096 bits.

JWT is exactly three nonempty canonical-base64url segments with the overall16384-byte bound; header at most1024 decoded bytes, payload at most8192, signature256..512. Header exact fields are `alg:"RS256"`, `typ:"JWT"`, and `kid`; reject `none`, algorithm confusion, `crit`, `jku`, `jwk`, `x5u`, `b64` and unknown headers. Unknown key ID fails without lookup/fetch. Signature length must equal selected RSA modulus byte length. Verify `crypto.verify("RSA-SHA256", ascii(headerSegment+"."+payloadSegment), {key,padding:crypto.constants.RSA_PKCS1_PADDING}, signature)` before trusting payload claims. No RSASSA-PSS or HS256 fallback.

Require these payload claims: `iss`, `aud`, `sub`, `exp`, `iat`, `nbf`, `jti`, `repository`, `repository_id`, `repository_owner_id`, `run_id`, `run_attempt`, `workflow_ref`, `workflow_sha`, `ref`, `sha`, `event_name`, `environment`. All context claims are strings. Require exact issuer/audience/subject and signed-policy identity/workflow/ref/event matches. JWT `environment` must equal policy `protected_environment`, exactly `workshop-staging-publish`; it must never be compared with policy `environment`, whose value `staging` denotes the product stage. A positive fixture has policy `environment:"staging"`, policy `protected_environment:"workshop-staging-publish"` and JWT `environment:"workshop-staging-publish"`. Negative signed JWT fixtures use `environment:"staging"`, another protected environment, a missing environment and nonstring environment; each is rejected. `aud` must be one string, never an array. Run ID is positive decimal up to20 digits; attempt is canonical string1..1000; compare with the exact expected run/attempt context. The expected context has exactly `run_id` and numeric `run_attempt`; its origin is not authenticated by this byte primitive. `sha` must equal policy `workflow_sha` for this fixed non-reusable workflow_dispatch contract. The requested build `source_sha` is separate and is not authenticated by this assertion. No reusable-workflow support is inferred from `job_workflow_*`.

Timestamp claims are safe integer UTC seconds: `exp > now`; `exp > iat`; `exp-iat <= 300`; `iat <= now+30`; `now-iat <= 300`; `iat-30 <= nbf < exp`; `nbf <= now+30`. No expiration grace. `jti` is an ASCII noncontrol string1..256 bytes; require its presence but claim no durable one-time replay protection. `now` is an explicit argument only for pure byte tests; installed wrappers take trusted local `Date.now()` and `performance.now()` internally and accept no injected clock.

Allow additional documented claims only: `run_number`, `actor`, `actor_id`, `workflow`, `repository_owner`, `repository_visibility`, `ref_type`, `ref_protected`, `head_ref`, `base_ref`, `runner_environment`, `job_workflow_ref`, `job_workflow_sha`, `environment_node_id`, `enterprise`, `enterprise_id`, `issuer_scope`, `check_run_id`. Preserve only required verified claims in the returned frozen record. Optional `ref_protected` accepts only boolean or literal string `true`/`false`; all other optional claims are bounded strings. Reject unknown claims to fail closed on schema evolution. Optional reusable-workflow claims do not authorize a reusable workflow.

## Runtime bearer is explicitly unsupported

`authenticateActionsRuntime()` synchronously throws a redacted `missing_dependency` without inspecting arguments, reading environment/stdin, invoking callbacks, loading policy/toolkit, creating timers or performing any I/O. It never returns an identity. `verifyInstalledGithubOidc` returns an OIDC record only. Hash equality, environment equality, a valid OIDC token and decoded `ACTIONS_RUNTIME_TOKEN.scp` cannot produce the current uploader's `{repository_id,repository_owner_id,run_id,run_attempt,runtime_service_origin}` receipt. Existing injected `authenticateRuntime` contracts are not wired to these new modules.

GitHub's official artifact utility JWT-decodes runtime `scp` to obtain backend UUIDs; it does not authenticate a numeric originating attempt. Runner source sets runtime token and OIDC request token from the same endpoint access token, but this is not a reviewed Results bearer attestation protocol. Any future positive authenticator requires a separate design/gate, documented provider behavior and staged evidence of the exact bearer/Results-origin/numeric-run/attempt binding. No live credentials or protected API calls belong to Stage1A.

## Owner inputs, retained blockers and evidence limits

The engineering choices above are frozen for independent review; they are not claims that the owner has installed trust. Actual signing public key/fingerprint, accepted policy envelope digest/minimum epoch, numeric owner/repository IDs, exact protected subject/workflow SHA and authenticated normalized JWKS snapshot remain owner-selected activation inputs. This milestone may use ephemeral local test keys only in the two test files. Those keys, metadata fixtures and success records never authorize a production root or provider acceptance.

The root path/provisioning authority, clock/freshness/revocation assumptions and subject policy require owner/security acceptance before an installed production policy can be provisioned. Future audience changes, online JWKS refresh, runtime bearer authentication and production policy are scope changes. Toolchain tree approval, seven moderate toolkit advisories, `buffers` licensing, complete immutable installation, independent approval, WIF, raw REST readback, worker/factory wiring and staging/production activation remain separate blockers. Existing helper/tree tests prove mechanisms against fixtures, not a reviewed installed toolkit or licensing disposition.
