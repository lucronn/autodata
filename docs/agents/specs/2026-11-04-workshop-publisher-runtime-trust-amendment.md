# Workshop publisher runtime trust protocol amendment

Status: **pending owner trust decision; blocked draft**. Source candidate: `4d82e413e04fb2401ac7bc28dc828375ac662180`. This document is an additive proposal, not a change to Stage1A authority. Canonical gate: `docs/agents/pre-implementation-gate.md`. ## The exact blocker and owner decision

The candidate's `publisher_identity.mjs::authenticateActionsRuntime()` unconditionally throws `missing_dependency`. `publisher_artifact.mjs::uploadReleaseInternal()` requires an injected `authenticateRuntime` callback returning numeric repository/owner/run/attempt identity. No supported authenticated GitHub Results credential introspection or documented cryptographic mapping from the Results bearer to numeric run/attempt was found. The official artifact toolkit decodes its token for routing; decoding is not signature verification or issuer-authenticated numeric identity. Matching environment variables, successful upload, JWT-shaped bytes, TLS to a Results endpoint and successful OIDC verification do not close that gap.

The owner must choose one of these mutually exclusive policies in a separately reviewed decision record:

1. **Independent bearer proof required:** retain the blocker. Do not implement an affirmative authenticator or substitute OIDC/environment/readback consistency. Resume only with independently reviewed official authenticated proof binding the specific Results credential to repository ID, owner ID, numeric run ID and attempt, including issuer, audience, key origin and replay semantics.
2. **Protected-runner trust accepted:** accept the runner and reviewed control process as the boundary that associates its injected opaque Results bearer with a verified OIDC run/attempt. Adopt the protocol below. Its guarantee is an authenticated runner-origin statement about an upload plus independently authenticated artifact bytes. It does **not** cryptographically authenticate or introspect the Results bearer itself. A compromised runner/control process or stolen usable bearer/signing authority remains outside this guarantee. Do not label any result `runtime_bearer_authenticated:true`.

No choice is inferred from this draft, historical planning approval or the existence of an OIDC primitive. Until the owner explicitly records choice 2, the current requirement remains blocked.

## Research basis and limits

- [Official toolkit token utility](https://github.com/actions/toolkit/blob/main/packages/artifact/src/internal/shared/util.ts): published `@actions/artifact@6.3.1` utility uses `jwtDecode` for routing; no authenticated Results-token introspection or numeric mapping was found. - [Runner injection](https://github.com/actions/runner/blob/main/src/Runner.Worker/Handlers/NodeScriptActionHandler.cs) explains the trusted runtime injection boundary. It does not turn caller-supplied environment into proof.
- [Artifact REST metadata](https://docs.github.com/en/rest/actions/artifacts#get-an-artifact) identifies the artifact and workflow run; it does not independently establish an originating run attempt. [Exact-attempt REST](https://docs.github.com/en/rest/actions/workflow-runs#get-a-workflow-run-attempt) validates the selected attempt, but cannot alone prove that an artifact originated in that attempt.
- [Fulcio GitHub principal mapping](https://github.com/sigstore/fulcio/blob/main/pkg/identity/github/principal.go) supports the proposed OIDC-derived run-invocation signing identity. A cryptographically verified certificate/bundle must supply the exact run-invocation URI; constructing that URI from the requested context is not verification.

The moving `main` links are explanatory research references, not accepted executable pins or complete compatibility receipts. Pin reviewed source revisions, verifier/tool hashes, Fulcio/Rekor trust data and accepted certificate extension mapping in the later checkpoint. No live credential, upload, signature, API, SDK import or runtime test occurred here. Failure to find introspection is a documented support gap, not a claim that undocumented GitHub behavior can never exist.

## Proposed protected-runner protocol

The protocol is proposed only for `staging`, repository `lucronn/autodata`, protected environment `workshop-staging-publish`, event `workflow_dispatch`, ref `refs/heads/master`, and separately reviewed exact control-workflow SHA. Requested build `source_sha` stays distinct from `workflow_sha`; OIDC `sha` authenticates the fixed control workflow under the existing Stage1A contract. No production policy is introduced.

1. **Establish trusted process and policy.** A future separately gated protected control supervisor loads an independently installed owner policy and reviewed executable/toolkit tree. Owner policy must explicitly select `trust_model:protected_runner_oidc_post_upload_v1`, approved Results origins, numeric repository/owner IDs, exact control SHA/ref/environment, verifier roots and bundle rules. Stage1A's signed purpose `autodata.publisher.stage1a.offline`, `upload_enabled:false` and `runtime_bearer_authentication:unsupported` remain unchanged and cannot authorize this policy. A separate runtime policy schema/installed loader is required in a later gate; no new policy is installed here.
2. **Authenticate OIDC context.** Verify signed OIDC issuer, one exact audience, subject, repository/owner numeric IDs, environment, control SHA/ref/event, numeric run ID and canonical attempt with the existing strict bounded cryptographic/time rules. A new runtime audience/purpose requires its own signed schema, not reuse of `urn:autodata:publisher:stage1a:offline`. Run ID is canonical positive decimal string at most20 digits; attempt is integer1..1000 in protocol objects and canonical decimal string in OIDC. Caller context and environment are consistency checks only. Reject older/rerun attempts and any mismatch before starting the SDK child.
3. **Associate the opaque credential at the runner boundary.** The trusted supervisor captures runtime injection once from the protected runner, associates it with that verified OIDC context, and passes only necessary variables to the isolated reviewed SDK child. Results bearer stays opaque: no decoder result, secret hash or bearer bytes enter a receipt, statement or log. Require exact approved HTTPS Results origin, no userinfo/query/fragment or fallback origin; redirects cannot broaden authority. The SDK child receives neither separate REST read credential nor signing authority. Explicit caller data/passive validation records cannot mint a production runner-boundary capability. No exported `verified:true` constructor or injected callback result supplies installed authority.
4. **Upload once.** Before upload, freeze reviewed source/configuration/candidate/rollback identity and exact private inner `release.zip` bytes. Use the pinned official toolkit to upload exactly that file, fixed artifact name including source/run/attempt, overwrite false, retention7 days, compression0, hidden files false. Retain returned immutable artifact ID, digest and size. Missing/unsafe IDs, omitted/wrong digest, any positive `digestMismatch`, size over16MiB, failed child cleanup, timeout or cancellation is terminal. Upload success alone produces no accepted publication.
5. **Read back independently by ID.** Use a separately supplied bounded `actions:read` REST credential, never the Results bearer, to request fixed-repository artifact metadata and the original outer ZIP bytes for that exact immutable ID. Reject metadata ID/name/digest/size/repository/run/head-SHA mismatch, expired/stale or inadequate retention and redirected credential leakage. Hash the exact original outer bytes and require equality with both REST and SDK digests and size. Safely decode exactly one `release.zip` with the existing bounded outer ZIP rules; compare inner bytes byte-for-byte with the frozen upload bytes and preserve the existing inner/member/manifest digest distinction. Repacked or extracted-file SDK downloads are unacceptable. An exact-attempt REST response confirms attempt identity/status/source, never supplies artifact-attempt provenance by itself.
6. **Sign only the completed observation.** After all upload/readback checks and owned resource cleanup succeed, produce the existing in-toto `workshop-upload/v3` statement (`publisher_adapters.py::upload_statement`). Its subject is `github-actions-artifact:<immutable ID>` with original outer SHA256; exact `binding_core` includes owner/repository/run/attempt/control/source/configuration/candidate/rollback identity, outer/inner/member digests and sizes, metadata times, manifest and source-statement references. Exact `upload_evidence` includes toolkit lock/control SHA, numeric run/attempt, upload-request digest, returned ID/digest, approved runtime origin, canonical metadata-projection digest and upload start/finish times. No signature before readback, no self-referential upload-statement locator inside `binding_core`, no secret or raw OIDC token in the statement. The statement is separate evidence and is not added to or used to rewrite the already hashed artifact.
7. **Verify the signer and originating attempt.** Proposed signing profile is a separately pinned Sigstore/Fulcio keyless verifier that cryptographically validates bundle/certificate chain, issuer and exact workflow identity, certificate time and transparency/checkpoint policy. It must derive `run_invocation_uri` from authenticated certificate extensions mapped from signed GitHub OIDC, exactly `https://github.com/lucronn/autodata/actions/runs/<run_id>/attempts/<attempt>`, plus authenticated exact `workflow_sha` and `workflow_ref`. No URI synthesized from requested context, generic subject-only signature, caller dictionary, signature-valid boolean or arbitrary certificate URL is accepted. If the chosen supported profile cannot expose authenticated exact attempt identity, keep blocked and redesign before implementation. Fresh OIDC for signing must match the originally verified run/attempt and exact policy; token refresh cannot silently change attempt or source/control identity.
8. **Consumer acceptance.** An independent consumer verifies raw statement digest, cryptographic bundle and signer identity, all statement/context equalities, original artifact readback and exact-attempt completion/status/time window. Keep existing `validate_upload_statement`, `_signed_identity`, metadata/archive/image/source/approval checks. Signing/uploading may occur while the attempt is running; final acceptance waits for the exact attempt's successful completion and bounds upload times within that attempt. Output may claim publication verification under the explicitly accepted runner trust model only. It grants no deployment, readiness, merge or production authority. A signature proves the accepted runner's assertion and bytes; it does not elevate Results bearer provenance into independent cryptographic proof.

## Required owner inputs before a new gate

- Explicit choice1 or choice2 above, accepted runner-compromise scope, approved runner class/isolation and control-code provenance. Untrusted source build steps must not access supervisor credentials/signing authority.
- Numeric repository/owner IDs, exact protected subject/environment/workflow SHA/ref, policy epoch/digest/validity, separately authenticated OIDC JWKS and future runtime audience/policy/installed source. No production values or fixture keys by default.
- Reviewed Results origin allowlist, toolkit/runtime/helper hashes, separate REST credential permissions/custody and bounded redirect/download policy; documented readback permission denial behavior.
- Sigstore/Fulcio/Rekor and verifier exact source/binary pins, trusted roots/checkpoint/identity-extension mapping, statement storage and immutable retrieval rules. No assumed certificate extension or signing service is an owner approval.
- Replay decision: verify expected run/attempt explicitly; never select latest by artifact name. Proposed acceptance is repeatable verification of the same immutable binding within validity, not one-time deployment authorization; a requirement for consumed/nonreplayable authorization needs a separately designed durable ledger.
